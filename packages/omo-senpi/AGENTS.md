# omo-senpi

Native Senpi TypeScript extension adapter for oh-my-openagent. Telemetry uses the SDK-free `@oh-my-opencode/telemetry-core/injected` entry; its lazy transport imports `#omo-telemetry-posthog-runtime` only on the first capture (source `src/components/telemetry/posthog-runtime.ts` -> plugin `extensions/omo-telemetry-posthog.js`); keep build freshness, required installation artifacts and bundle audits aligned with every sidecar named below.

Adapter-only: this package may depend on harness-neutral core packages plus the Senpi-coupled `@oh-my-opencode/senpi-task` engine, but those packages must not import Senpi, Pi packages, or this adapter through their harness-neutral entrypoints. The Senpi runtime boundary stays here.

## Anatomy

| Path | Purpose |
|------|---------|
| `package.json` | Private workspace package `@oh-my-opencode/omo-senpi`; exports `.`, `./extension`, `./install`, `./agent-home` (-> `src/components/agent-home/resolve-agent-home.ts`), and `./onboarding/session-history` (-> `src/components/onboarding/session-history/index.ts`), all to `src/` TS. Maps 20+ private `#...` runtime aliases to implementation files (`#omo-task-runtime` -> `src/extension/omo-task.ts`, plus telemetry/posthog/otlp/recovery, thread-client, wake, feedback, claim-receipt, device-account, memory doctor/memfs/palace/commands/sync, recall-store, session-history, device-service, computer-use, agent-toolkit-sdk, `#senpi-private-fds`, and the pinned `#bunshin-ts-dep/*` install); the plugin manifest remaps these to their generated bundles — `package.json` is the authoritative alias map. |
| `src/` | Adapter source; own AGENTS.md, with deeper files for `extension/` and the eight deep components (`memory`, `task`, `lsp`, `telemetry`, `init-deep-advisor`, `thread`, `builtin-mcps`, `x-search`). Small components are documented in the Components section here (`src/AGENTS.md` defers to this file). `senpi-test-runtime.ts` imports real host modules for tests. |
| `src/extension/` | Senpi ExtensionAPI composition layer. It validates the required API surface, registers global and per-component disable flags, and wires components defensively. Own AGENTS.md. |
| `src/components/` | Live components, in `src/extension/component-list.ts` registration order: `config-startup`, `model-profile`, `bundled-skills`, `skill-commands`, `native-badge`, `onboarding`, `init-deep-advisor`, `onboarding-scan`, `side-panel`, `telemetry`, `ultrawork`, `skill-pointers`, `ulw-execute-continuation`, `ulw-loop`, `js-kernel-guard`, `todo-fanout-reminder`, `question-gates`, `claim-receipt`, `git-master`, `fallback-architect`, `ast-grep`, `builtin-mcps`, `lsp`, `x-search`, `computer-use`, `feedback`, `device-service`, `remote`, `browser-bridge`, `desktop-toolkit`, `claude-code`, `comment-checker`, `thread`, `memory`, and `config-watch` (35 factories; `task` is passed in by the extension entry). Documented alongside them are the `config-resolution` loader helper and the `agent-home` resolver (neither is a registered component). |
| `src/install/` | Local Senpi installer and uninstaller helpers. They add or remove the absolute plugin path in the canonical agent directory resolved by `resolveAgentHome` (`~/.omo/agent` for an omo installation, an explicit `OMO_`/`SENPI_`/`PI_CODING_AGENT_DIR` when set, the flat `~/.omo` and `~/.senpi/agent` layouts only as detected fallbacks). The generated local launcher pins that same directory for the engine it spawns. |
| `plugin/` | The single Pi package `@code-yeongyu/omo-senpi`: generated `extensions/` bundles, generated skills, the tracked `runtime/dag` SDK, and plugin-local build scripts. Own AGENTS.md. |
| `scripts/qa/` | Live Senpi QA drivers, continuation probes, and mock providers; the real harness proof for adapter changes. Own AGENTS.md. `scripts/expect-exit.mjs <expected> -- <cmd...>` asserts child exit codes. |
| `skills/` | Native Senpi skills authored directly against the Senpi tool surface (not ported from Codex or the shared pool): `dag-library`, `give-me-tips`, `hyperplan`, `init-deep`, `mass-ulw`, `onboarding`, `ultrawork`, `ulw-loop`, `ulw-plan`, `ulw-research`, `visualize`. Own AGENTS.md. The credential-gated `x-search` skill is **not** in this pool: `plugin/scripts/stage-x-search-skill.mjs` copies `src/components/x-search/skill/SKILL.md` into `plugin/skills-conditional/x-search/` (kept out of `pi.skills`) and the `x-search` component contributes that path via `resources_discover` only when an xAI credential exists. |
| `vendor/` | Built publishable output of `@sisyphuslabs/bunshin-ts` and `@sisyphuslabs/bunshin-ts-relay` (not on npm; proprietary, each with its LICENSE), bundled only into `plugin/runtime/bunshin-ts/sdk.js`. `vendor/PIN.json` records the source commit, the publish manifest and a sha256 per file; the sync's one change to the build output points the runtime JS's npm dependency imports at `#bunshin-ts-dep/<name>` (package.json `imports`, the exactly pinned install), because senpi's Bun extension registry claims bare names like `@sinclair/typebox` (its typebox 1.x) for every importer in the process; `src/bunshin-ts-vendor.test.ts` fails when the bytes drift or anything imports either package by name. Re-sync from local checkouts of both sources: `bun packages/omo-senpi/scripts/sync-bunshin-ts.ts --bunshin-ts <checkout> --bunshin-ts-relay <checkout> [--commit <package>=<sha>] [--write]`, then rebuild the plugin. |
| `test-support/` | `fake-extension-api.ts`: `FakeExtensionAPI` + fake event dispatch; records commands, flags, messages, tools, renderers, MCP registrations, and dispatched results for hostless tests. |

The v1 install surface is local-path only. Install the built Pi package from `packages/omo-senpi/plugin`; do not document npm, git, or marketplace distribution for this adapter until that exists in code.

## Components

- `desktop-toolkit`: `omo_desktop_toolkit` request/grant channel for app-hosted toolkits; only sessions offered toolkits load `#omo-desktop-toolkit-runtime` (others keep the unavailable acquisition tool). Discovery starts after first paint (first real `before_agent_start` joins); failed retries run in the background, back off across turns (next, +2, +4; stop after 3), so an unanswering app never holds a prompt; preview passes start nothing. App MCP tools register as native `desktop_<name>` (name `^[a-zA-Z0-9_-]{1,64}$`, object schemas; invalid/already-registered skipped); shutdown aborts discovery and clears the grant; grants keyed by session ID — execution resolves only the calling context's session, never the registering one; each discovery/call reads the bearer file afresh over dependency-free Streamable-HTTP JSON-RPC with fixed non-secret failures. A `host` offer (#11897) runs the same discovery for host attachments (`_meta["senpi/host-tool"]` naming a public `host_tool_names` callable; never registered standalone) — a confirmed grant sets `senpi:host-tool-route` owned by the granting session, only its owner's shutdown clears it, a lost route clears its grant for re-confirmation, and `omo.toolkit.executeHostTool` runs the app-side call in the granting session's cwd.
- `device-service` (#12051): bootstrap sidecar `#omo-device-service-runtime` (loads after first paint to keep omo.js under its byte budget) runs only in the top-level interactive TUI (first `session_start` with `mode: "tui"` — RPC mode binds a real UI, so `hasUI` is not enough), only in an engine an omo launcher started (absolute `OMO_BIN`), never under `CI`, never in a task child, once per process (`globalThis` latch under `Symbol.for("omo.device-service.bootstrap")`). It spawns `$OMO_BIN remote bootstrap --json` unref'd (10-minute deadline; `omo account show`, pinned install, mutual-proof connection, refresher, adopt, endpoints). The worker's last JSON line becomes one `ui.notify` warning for every stop except `signed_out`, `store_unavailable` and `not_published` (#12656, debug log only); `connected` is silent; it never writes the attach setting (`omo remote control`). The same hook also starts the agent-dir registrant (#12379) in every `tui`/`rpc` engine (desktop engines run `--mode rpc --multi-session`), with the same CI/task-child/`device_service.enabled: false` skips but WITHOUT the `OMO_BIN`/UI gates, once per process (latch holds the instance), inside an `AsyncResource` captured at omo.js module top level so senpi's per-session handle ledger never reclaims its socket/watcher/timers. `device-service-core` `startAgentDirRegistrant` holds one unref'd local-API connection and sends `endpoints.register {agent_dir}` for the engine's resolved `ctx.agentDir` once per new (connection, device id) pair (at each proof and on replayed/later statuses naming a new device; signed-out or refused/failed register resets); new connections come from the endpoint file appearing (non-persistent watch on the state dir or nearest existing ancestor, armed before the first existence check) or the previous connection closing; connect retries bounded at 250 ms / 1 s / 4 s; engine exit does not unregister.
- `remote` (#13412): TUI `/remote` command (`components/remote/tui/`), person input only: each action runs ONE `$OMO_BIN remote <verb> --json` process (`run-omo.ts`, imported only by `command.ts`) and renders its typed answer, so no device-service client enters the engine bundle. Verbs `status`, `devices`, `sessions`, `enable`, `disable`, `control`, `open`, `model`, `interrupt`, `close` pass through; `send <device>/<session> <text>` puts the text after `--`; `attach` cannot run inside the TUI and names the `omo remote attach` command for a new terminal. Bare `/remote` is a picker (device → session → send/interrupt/close/attach); without an absolute `OMO_BIN` it says so and runs nothing.
- `config-startup`: shared lock+journal migration engine (`runSenpiStartupMigration`, legacy groups `2026-07-opencode-config-unification` for `oh-my-*` files and `2026-07-codex-config-jsonc` for `~/.omo/config.jsonc`) plus the Native-only routing-notice plan `2026-09-opencode-routing-notice`, then loads the profile-selected `[senpi]` view via `config-resolution` (`loadSenpiOmoConfig` = `loadOmoConfig` with `harness: "senpi"` + `resolveModelReferences` catalog expansion); migration results and config diagnostics surface once on the first `session_start` via the host notification UI (logger fallback). `native-badge`: publishes the native footer status badge into the TUI status line.
- `onboarding`: first-run flow claimed once per state dir on the first real interactive UI prompt (`claimOnboarding`), not `session_start`; explicit `--onboard` starts immediately in TUI. The shared setup scan (#10478) loads lazily, once, only after a claim succeeds (never in `register()`; fail-open) and feeds the migration inventory (sign-ins, custom providers, skills, MCP servers); since #10481 the first onboarding turn runs with `sessions: false` (#10480 — history arrives as the bounded background `onboardingHistorySummary` next turn). Tool bodies (`tui-memory-runtime.ts`, `session-history-tool-runtime.ts`), the TUI scan assembly, the `omo.onboarding.understand`/`.skip`/`.stop` handler bodies, understanding start and the validating apply ship in `extensions/omo-onboarding-scan.js` and load on first use (a failed sidecar load answers unavailable with the reason); the entry bundle carries only definitions, the applier shell and the state RPC. `omo.onboarding.state.get`/`.complete`/`.reset` share one state between TUI and desktop: a held claim reports `inProgress` while its owner runs (dead/pid-reused/ownerless >24h claims are taken over), only a finished onboarding writes `onboarding-completion`, a released claim never erases a completion, `reset` clears both. Also serves the desktop thread import over RPC (`omo.onboarding.projects`/`.sessions` + streamed events, read-only filesystem scans touching no model and no session); `onboarding_understand` returns candidates only and `onboarding_memory_apply` writes only the user's selection through `omo.memory.facts.apply`, with crash-recovery envelopes in `<facts>/applied/<batchId>/` finished by the facts maintenance reconcile or a same-`batchId` retry.
- `onboarding-scan`: `omo.onboarding.scan`/`.apply` RPC (#10478). The scan streams `omo.onboarding.scan.event` frames (`source_started`, `item`, `source_done`/`source_failed`, `done`) from `omo-native/bin/lib/setup-stream.js` (the same stream `omo setup` consumes), then `projects` and `sessions` from the engine session-history module (#10479), counting `{found, read, cap: 5000}` with digests held in memory only (nothing reaches disk before consent); at most 8 retained scans (random scanId) plus the last captured credential store are held for the whole engine process (desktop scans on one session, applies on another). Custom providers off unless requested; no model read, no socket opened. Apply re-reads every requested stage's targets and compares content hashes — anything changed answers `{kind:"stale", reason, paths}` and nothing is written; retained scans older than ten minutes answer stale; credential additions go through the engine's own store (`modelRegistry.authStorage`, captured at `session_start`) under its lock (mid-apply token refresh merges, never reverts; no store → refuse rather than write unlocked auth.json); a scan is marked `applied` synchronously and a second apply refused (applied scans still count toward the 8-scan cap, #12509/#12527). `omo.onboarding.understand` (+`.skip`/`.stop`, #10480): with `consent: true` and the caller's model it runs the memory facts extractor's launch path (`launchFactsInProcess` + `record_fact`) over digests + per-project AGENTS.md, streams step/fact/budget events and returns candidates without writing memory. Runtime ships as `extensions/omo-onboarding-scan.js`, lazily imported.
- `init-deep-advisor`: tracks init-deep state (coverage, drift, git-exclude managed blocks) and ships its own QA scripts (`qa-snapshot.sh`, `qa-managed-block.sh`, `qa-rpc-driver.mjs`). Own AGENTS.md.
- `side-panel`: opt-in right column (`side_panel` in `omo.json`, default off; `--omo-side-panel` forces on for one run — senpi coerces boolean flags to `true` and rejects `--no-` forms, so only `omo.json` switches it off); the entry carries only the registration shell (`index.ts`: flag, `/side-panel-diff` when possible, one forwarder per event), the runtime ships as `extensions/omo-side-panel.js` loaded on the first panel-on session. Host coupling isolated in `host-surface.ts`: zero-height anchor widget + pi-tui `hstack` wrap, original root restored on `session_shutdown` (fires new/resume/fork/quit; `session_before_switch` unused — cancellable); a renderer without the layout seam falls back to a widget block (an install-once notice then names the fullscreen column), headless renders nothing; tool/message/turn handlers start reads and return at once (the host awaits them); mode switches move widgets without re-running factories. Pure row builders in `sections/` (session, context, usage, agents, tools, location, files, goal, memory) never touch the host; data seams: `panelFactsFrom(eventCtx)`, `getContextUsage()`/`getUsageTotals()`, and the task record store (`parent_session_id` scoping); 1s repaint only while a child runs. Files section via host `exec` `git status --porcelain=v1 -z` + `--numstat` on a 2s floor (feature-detected; branch from `.git/HEAD`, no subprocess); usage section (off by default) draws engine subscription-limit records only (`pi.getSubscriptionLimits()`, no own network; `usage/accounts.ts` picks the serving account under an ORDERED provider-id list for senpi's renames, re-read every turn; `usage_poll_seconds` retired). Rows paint OSC 8 `omo-panel:` hyperlinks — the host's only click path (`side_panel.clickable` off drops paint+hook; `openUrl` claimed while mounted, foreign URLs handed back). Clicked child/diff/goal rows open a shared viewer (`data/child-output.ts` via `#omo-task-runtime`; viewer owns the wheel while open; height clamped by `popups/viewport.ts`); the goal store re-parses only on `mtime`/`size` change (no goal event exists — rides the refresh); suspended children show `suspended` (`suspension_reason` folded for live records only; ordinary suspension shows solely as non-resident `residency_state`); `runner_kind` + `execution_mode` give the card a `runs` line. Memory section: identity resolved once on mount, then durable state only (reflection park file, `facts-queue` backlog minus bookkeeping, `recall/ledger`+`pending` read-never-consumed, kibitzer `recall/sidecars/<base64url(session)>/wakes.ndjson` tail parsed fail-closed per line, floors on truncation; liveness deliberately absent).
- `ultrawork`: injects the ultrawork directive as a hidden custom message (`pi.sendMessage({customType: 'omo-ultrawork:directive', content: DIRECTIVE, display: false})` + `{action: 'continue'}`); on the idle path typed text is never modified; a prompt QUEUED mid-stream gets the directive appended inside that one message (senpi drains queues one message at a time — a separate hidden message would burn its own turn; appending preserves `/skill:` expansion). Word-bounded keyword-only match `\b(?:ultrawork|ulw)\b/i` fires on `ulw` as a word incl. skill names (`ulw-plan` etc.), not fused identifiers; overlapping keywords all load their surfaces. `skill-pointers/strip-quoted-regions.ts` blanks (offset-preserving) inline code, fences and injected `<omo-*-pointer>`/`<ultrawork-mode>`/`<omo-ultrawork-reminder>` blocks, so quoted or relayed mentions never arm (the telemetry classifier shares the filter); remaining guards are structural only: `omo-senpi-ultrawork-disabled` flag, `source === 'extension'` inputs, an existing matched tag pair (a lone open tag still arms). `/skill:ultrawork` passes through untouched (expansion already inlines the directive; a trigger only in the skill NAME does not arm). Directive authored senpi-native at `skills/ultrawork/SKILL.md`, shipped verbatim; `plugin/scripts/embed-directive.mjs` embeds it into `generated-directive.ts` and fails the build on non-senpi harness tokens (multi_agent, update_plan, codex, ...).
- `skill-commands`: rewrites the bare `/<bundled-skill> args` form to `/skill:<name> args` (#9042) before every other omo input handler (keeping `interactive`/`rpc` source, so the ulw-plan gate, ultrawork non-arming, skill-pointers dedup and continuation resets behave as for a typed `/skill:`; a registered command could only re-submit with the untrusted `extension` source); steps aside when a prompt template or command owns the name; a disabled/not-loaded bundled skill answers a warning notice instead of reaching the model; on `session_start` wraps the TUI autocomplete so each bare name takes its `skill:<name>` row at top level; `skill-commands/documented-commands.test.ts` fails when a shipped SKILL.md or Native guide names a backticked `/command` that neither a bundled skill, an omo `registerCommand`, nor an engine command provides.
- `skill-pointers`: ONE uniform keyword table (quoted/relayed regions blanked via `strip-quoted-regions.ts`, shared with ultrawork) injecting a hidden pointer per matched skill — `mass-ulw` (aliases incl. `mulw`, `meth`, `ulw mass`), `ulw-plan`, `ulw-loop`, `ulw-research` (each `omo-*:skill-pointer`, `display: false`); `ulw-research` also carries the `ultimate-browsing` COMPANION (no keyword of its own; rides every parent invocation incl. dedup paths, arming browsing lanes with `load_skills` — 0/23 research runs loaded it before). `mass-ulw` + `ulw-research` are BINDING only in fixed forms (`bindingForms`: the skill's slash command opening the prompt, or first word run/start/use/do/execute + keyword + connector/EOS with no `?`; Korean keyword + 돌려줘/실행해줘/써줘/해줘/돌려/실행해 closer) → `<omo-*-mode>` blocks requiring the skill read (mass-ulw also `references/planning.md`) before any other tool call, and workflow runs over inline work; every other mention keeps the conditional pointer. A `bunshin` pointer (on `bunshin`, `machine mesh`, fleet-possessive mentions or fleet machine nouns; bare `fleet` deliberately does not fire, #13446) has no packaged skill — it teaches the `OMO_BUNSHIN_TS_SDK_ROOT` eval import; `ulw-loop`'s pointer teaches the `OMO_AGENT_TOOLKIT_SDK_ROOT` agentToolkit import; `ulw-plan`/`ulw-loop` keep conditional pointers. No cross-keyword negatives (overlaps all fire); stateless (re-injects per mention); structural dedup per skill only (`extension` source, raw `/skill:<name>` for that skill, expanded `<skill>` block); queued prompts get pointers appended inside one message. Gated by `omo-senpi-skill-pointers-disabled`.
- `ulw-execute-continuation`: records the `agent_end` outcome (Senpi analog of Codex's Stop hook) and, on `agent_settled`, reads `.omo/boulder.json` — first `reconcileStaleWorks` with the sessions directory from `agent-home` (`resolveAgentSessionsDirectory`), so a dead session's work demotes to `paused`+`stale_since` instead of staying `active` forever (#8413; resuming restores `active`) — and injects a continuation directive when this session owns an active/paused Prometheus work plan. Uses `senpi:<session_id>` state from the `ulw-execute` skill, suppresses repeats by a `work_id:updated_at:completed/total` signature, caps consecutive continuations at 8 (reset on user input); registers before `ulw-loop` so boulder work wins.
- `ulw-loop`: detects active ulw-loop state (read in-process through the SDK) and injects continuation guidance on `agent_settled` when the cwd has an incomplete run (`agent_end` is footer upkeep + outcome recording only); defers to `ulw-execute-continuation` when boulder state is continuable for the same session.
- Continuation preconditions for BOTH producers (`agent-end-eligibility.ts`): the decision happens on `agent_settled` ("no automatic retry, compaction, or queued continuation will run"), so a retry-owned turn, a turn held for required auto-compaction, and a user abort landing after `agent_end` (the host mutates that event object while its boundary is open) all block continuation WITHOUT consuming a slot or dedupe signature. The recorded outcome must also be continuable in the host's terms: last assistant stopped `stop`/`length` or as a malformed (tool-call-less) `toolUse`, no refusal/sensitive stop under `fallback-architect/detection.ts`, no aborted error `toolResult` after it. Every skip is logged; live proof `scripts/qa/policy-continuation-e2e.mjs`.
- `todo-fanout-reminder`: when ultrawork is armed (shared `SessionArming` ledger, so compaction semantics stay consistent) and the todo tool records its first task-adding result (`op` `init`/`append`), appends a once-per-session `<system-reminder>` to that result: size the work and todos, compute the fan-out decision explicitly (parallelism gain vs spawn/coordination overhead), always surface the delegation decision with per-part category routing and reasoning (working directly is fine when fan-out does not pay, but the decision is stated either way), keep the todo list obsessively fresh. Gate resets on accepted `session_compact`, clears on `session_shutdown`, anonymous slot on hosts without session ids. Gated by `omo-senpi-todo-fanout-reminder-disabled`.
- `question-gates`: one `tool_call` handler on `ask_user_question`/`request_user_input` setting `required: true` in place when the call gates an action (#9774) — a model that omits the flag still gets senpi's refusal instead of "continue on your best judgment". Primary contract: header exactly equals a pinned `PINNED_GATE_HEADERS` entry (`Approval` = ulw-plan approval gate; `Authorize` = ulw-plan final authorization, mass-ulw scope/spend/irreversible decisions; `승인`/`권한`); all fit senpi's 12-char header limit (enforced before extensions see the call). Fallback: option label starting `approve`/`authorize`. Question text never read; flag never set false; one `debug` line per forced call. Disable with `--omo-senpi-question-gates-disabled`.
- `claim-receipt` (#10777): at `agent_before_settle` classifies the final answer's own prose for pass/done/already-exists claims (EN+KO; code spans, fences, quotes, blockquotes, relayed reports, handoff `Ask:`/`Now:`/`Next:` lines, negated/conditional sentences ignored) and matches each against the live branch (`classify.ts`/`evidence.ts`/`match.ts`, pure). Parsers + matchers ship as `extensions/omo-claim-receipt.js` behind `#omo-claim-receipt-runtime`, loading on the first finished answer that gets that far (failed sidecar load skips that answer, retried next one); the entry bundle keeps hooks, session state, `verdict.ts`. A check counts only when a command actually invokes it: `shell-words.ts` splits shell segments (subshells + `$(...)`, heredoc bodies dropped); `invocations.ts` decides by executable + subcommand through `cd`, env assignments, shell keywords, `env`/`time`/`timeout`, `bash -c`, `ssh host '<cmd>'`, `bunx`/`npx`, `uv`/`poetry run`, `python -m`, `make`/`just`, heavy-slot wrappers; `gh pr checks` / `gh run view|watch` / status-rollups are CI readouts; `echo bun test`, `grep vitest`, commit messages never count. Eval cells: a string literal or list argv counts only in a positive allow-list of command positions (runner-call first arg, `$`/`sh` template tag, `command:`/`cmd =`/`script`/`job` field, `[name, command]` pair, `for ... in [...]` list); otherwise text — an unknown helper fails toward not-a-run. A claim is supported only by a matching-kind check that passed before the answer and after the last edit-tool change; flagged when no check ran (a lookup is never a check), when the latest decisive structured check (`tool.bash` results, terminal exit codes, `lsp_diagnostics`) failed, or an edit landed after the last pass; `exists` claims proven by lookups or any passing check; `done`/`works` not judged with no code edit; a monitor that failed/timed out is not a check; eval-cell failures/writes are never attributed. Output is boundary-only (never `continue`/`sendMessage`): an `omo-claim-receipt:verdict` record per claim-bearing answer and, at most once per user-sourced `input` (re-armed by accepted compaction), a visible `omo-claim-receipt:nudge`; a `*gate-reviewer` task spawn gets a `<claim-receipt-flags>` block. Shadow mode default: verdict records + logger always written, nudge + gate-reviewer block need `omo-senpi-claim-receipt-nudge` until replay precision ≥70% (#10802). Replay `scripts/qa/claim-receipt-replay.mjs`; live proof `claim-receipt-e2e.mjs`. Idea inspired by dinobot (roach, PolyForm Noncommercial); no dinobot code/tests/prompts used.
- `git-master`: appends a commit-attribution directive to git-master skill content from the `git_master` section of `omo.json` — `include_co_authored_by` (default `true`): one `Co-authored-by: sisyphus-dev-ai <sisyphus-dev-ai@users.noreply.github.com>` trailer per commit via `git -c trailer.ifexists=addIfDifferent commit --trailer` (git drops duplicates); `commit_footer` (default `false`): body footer. At most once per skill text (`<commit_attribution>` guard). Two channels: a `tool_result` hook on successful `read` results whose path ends in `git-master/SKILL.md`, and the task component's `createTaskSkillLoader` patching the resolved block for `load_skills` children. Settings lazy per event through `loadSenpiOmoConfig` (toggles apply without restart); both keys off → nothing appended.
- `fallback-architect`: when senpi's retry-fallback controller moves the session off `claude-fable-5` after a refusal or Usage-Policy rejection, injects one hidden `omo-fallback-architect:directive` telling the weaker active model to decompose and consult `task(category: "architect")` with self-contained per-part queries. Detection is extension-surface only: `message_end` refusal signal + `model_select` with `source: "fallback"`; `detection.ts` mirrors senpi `isClassifierRefusal` (`packages/ai/src/utils/stop-details.ts`) incl. stop-reason-first ordering. Fires only with an enabled `architect` category; a compact reminder rides each later user prompt until fable 5 returns — always hidden (`display: false`), typed text never rewritten (mid-stream: `sendCustomMessage` -> `agent.steer`, so no extra assistant turn; the old transform-append leaked into the user's bubble). Arming also emits one visible `omo-fallback-architect:notice` (`details: {from, to}`) framing the switch as an upgrade; `notice.ts` owns copy + a TUI renderer, and the stable customType + details ride senpi's event stream so GUI surfaces render it without senpi core changes. ## Notes

Session `process` children run on the session's own engine host (`p-<key>.sock` under `OMO_RPC_SHARD_ROOT` or `<agentDir>/rpc/shards`, routed by `src/components/task/shard-routing.ts`); a child's children stay on the birth host and `OMO_RPC_SOCKET*` never route task children; `rpc.sock` remains the operator endpoint (`omo daemon run`, thread-tool session creation, `omo daemon adopt`); `plugin/daemon-launch-spec.json` is the ONLY argv source for every host (`omo daemon`, child ensures, desktop server) — rebuild the plugin to change it, never hand-edit; `task.default_execution_mode: auto` routes to the session host when reachable and capable, in-process otherwise; no cap on hosts/children/memory (measured cost + rollback runbook in `docs/reference/omo-daemon.md`).

Lazy sidecar runtimes (registrars stay synchronous; runtime loads on first use; one import shared per process; a failed load is not cached and reports an actionable "reinstall omo, start a new session" error instead of an unhandled rejection; covered by build-freshness, installation-artifact and bundle audits): `/memfs` -> `#omo-memory-memfs-runtime` (`extensions/omo-memory-memfs.js`); `/palace` + `/people` -> `#omo-memory-palace-runtime` (`extensions/omo-memory-palace.js`); onboarding session-history -> `#omo-session-history-runtime` (`extensions/omo-session-history.js`); async thread/gateway operations -> `#omo-thread-client-runtime` (`extensions/omo-thread-client.js`; registrar captures the operator socket before loading, one runtime promise/client per facade, a failed load rejects `host_unavailable:<socket>` and the next operation loads again).
